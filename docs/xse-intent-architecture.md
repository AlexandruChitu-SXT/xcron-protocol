# XCron XSE: Intent-Package & Receipt Architecture

## Overview
This document formalizes the integration bridge between high-level Governance Layers (e.g., Fluxa) and the XCron Sovereign Execution Layer (XSE).

## 1. Intent Lineage & Batch Identity
Every execution is treated as part of a **Governed Intent Package**.
- **Batch ID**: A globally unique identifier (UUID/Hash) generated by the Governance Layer.
- **Idempotency**: XCron enforces that every `BatchExecutionIntent` carries a `batch_id`. The settlement layer (Smart Contract) maintains a bit-mask or hash-map of processed IDs to prevent double-spending or replay attacks.
- **Order Lineage**: Every `ExecutedOrder` in the receipt carries an `intent_index` that maps it back to the specific instruction in the original batch.

## 2. Secure Execution Receipts (Audit Artifacts)
XCron generates **Execution Receipts** inside the TEE (Sovereign Enclave), signed using the **Quantum Shield (ML-DSA)**.

### Receipt Semantics
- **Success/Partial/Failed**: Clear status flags for automated governance response.
- **Failure Context**: Detailed metadata (error codes, index of failure) to allow the Governance Layer to decide on "Retry", "Revert", or "Alternative Lane" logic.
- **Venue Agnosticism**: The receipt format is identical whether the execution happened on-chain (MultiversX) or off-chain (Binance), enabling unified accounting.

## 3. Separation of Concerns
| Layer | Responsibility | Component |
|-------|----------------|-----------|
| **Governance** | Decision, Allocation, Strategy | Fluxa / Agent Brain |
| **Execution** | Validation, Connectivity, Settlement | XCron XSE / Enclave |
| **Audit** | Evidence, Proof, Verification | Quantum Signed Receipts |

## 4. Failure State Expectations
- **Atomic Batches**: If any intent fails, the entire batch is rolled back (Atomic = True).
- **Non-Atomic Batches**: XCron executes as many intents as possible and returns a `PARTIAL_FAILURE` status with a list of successful vs. failed legs.
