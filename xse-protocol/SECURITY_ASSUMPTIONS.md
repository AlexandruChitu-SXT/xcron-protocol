# Security Assumptions

This document explicitly defines the security assumptions for the XCron Sovereign Enclave (XSE) execution layer. If any of these assumptions are violated, the security guarantees of the protocol may fail.

## 1. Execution Environment
- We assume the AWS Nitro Enclave hypervisor provides true cryptographic isolation.
- We assume memory pages within the enclave cannot be read or tampered with by the parent EC2 instance or the AWS virtualization layer.
- We assume the Attestation Document generated by the Nitro security chip is unforgeable.

## 2. Cryptographic Custody
- We assume the client (e.g., Fluxa) safely encrypts the Binance API Key and Secret using XSE's RSA-4096 Public Key *before* transmission.
- We assume the RSA Private Key exists *strictly and exclusively* in the volatile RAM of the Enclave and is never written to disk or logged.
- If the Enclave terminates, the memory is scrubbed, and the ephemeral private key is permanently destroyed.

## 3. API Key Constraints (Binance Side)
- We assume the user has correctly configured the Binance API Key with the principle of least privilege.
- **Withdrawals must be disabled** at the Exchange level. XSE assumes the key cannot withdraw.
- The API Key should be IP-restricted to the known Elastic IPs of the XSE Enclave nodes.

## 4. Intent Integrity
- We assume the Execution Intent (`execution_intent.schema.json`) is untampered between the User's authorization and the Enclave's ingestion.
- Replay protection relies on the `client_reference_id` and strict `expires_at` checks within the Enclave. We assume the time synchronization (NTP) provided to the Enclave is not heavily skewed by a malicious host.

## 5. Scope of XSE
- XSE assumes NO responsibility for the *strategy* of the trade. If a user authorizes a terrible trade intent, XSE will execute it perfectly.
- XSE is an execution arm, not a brain.
